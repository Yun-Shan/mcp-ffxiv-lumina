## 可执行边界用例

以下 fixtures 应使用很小的人工图验证图算法，而不是镜像实现或依赖 Wiki 实时页面。真实数据断言与算法 fixtures 分开统计。

1. **AND 成本**：目标 A，每次产出 2，需要 B×3 和 C×4；请求 A×3 时应兑换 2 次，展开 B×6 **且** C×8。不能将两种成本解释为二选一；应保留目标需要3/实际产出4的区别。
2. **多输出报价**：一次交易共同产出 A×2、D×1；请求 A×3 的成本只能乘2，不能按所有 receive 槽分别重复计费。未知 output count 不得默认为1。
3. **多跳容器**：源箱 C → 中间箱 B → A，保留两条有向边以及源箱副本叶；每一步记录 evidence，不仅展示首尾。
4. **数量向上展开**：开箱每次产出已知2，A需求3时需要2个箱；数量未知/只有概率分布时数量标 unknown，不能默认必出1或计算必需刷本次数。
5. **环与替代分支**：A←B←A 是环，B 同时有副本直接来源。只截断该路径上的环，仍保留 B 的副本分支。不得用全局 visited 误删 A←C←B 的合法共享节点。
6. **自环**：A←A 保留循环诊断而不递归，A另一个直接来源仍显示。
7. **深度上限**：限制为1时超出项必须有 `depth_limit` 或等价原因、未展开 itemId、仍可见的边证据。不得显示为“无来源”。
8. **分支上限**：保留稳定的前N分支，并报告已知总分支和省略数/未知省略数，确保重复运行同样输入顺序稳定。不能把截断后的集合称作全部获取方式。
9. **节点预算**：共享节点/大分支图达到预算时明确 budget 截断，保留当前已发现关系并结束；不能堆栈溢出或挂起。
10. **缺失关系**：商店、Item、CFC、DungeonBoss、Chest 任意一条引用缺失仍保留已证实原始 row ID 和 unknown；不得用不存在的 ID 生成一个虚构实体。
11. **币种不明**：unknown currency mode16 + raw2 只有原始编码，不能变成 Item:2 节点，更不能向上递归水晶来源。
12. **记录重叠**：BossChest 和 ChestItem 可能同箱，必须标记重叠不确定性；不能据两条记录将一个宝箱的保底产量相加、概率相加或概率独立相乘。
13. **来源与用途分离**：读取 ItemSupplement.SourceItemId→ItemId 时只向前解释产出、向反向索引查上游；不能把 ItemId 当开箱输入。消耗任务材料不能冒充任务奖励来源。
14. **不适用/未知**：零数量、缺失数量、未知成本编码、不可解析职业条件均有独立状态；不应静默过滤整个来源，也不应被当作免费、无条件来源。

## 独立审查结论

1. 本轮主图有意只把兑换的已知产量/成本进行数量递推；容器统一为一次开箱尝试，不从 Min/Max/Probability 反推保证数量。这是明确的原型边界，不应将链视为保证获得请求数量的计划。
2. 真实 `41680` 可保留两项 AND 成本并继续上溯，但基础武器 `40091` 的路径仍有未知货币或无支持来源。因此“至少看到一个副本叶”不能代替“AND全部成本已找到叶”的完整性判断。
3. 现有全量 SpecialShop 索引及本轮完整行中，未发现同一报价两个 receive 槽为同一个 Item 的案例。若以后出现，此原型尚未证明共同产出数量如何聚合；不得直接将当前按输出槽的路线当成最终通用实现。
4. CFC.Content 的语义应按内容类型/已验证关系识别。当前已核验的副本编号映射可以使用；向非 InstanceContent 类型扩展时不应无条件标为 InstanceContent ID。
5. 采集到的条件原始引用、职业类别和收藏价值只是证据，不代表已满足；未来正式接口仍需实现条件求值或明确返回未验证状态。
